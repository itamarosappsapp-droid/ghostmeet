# 05 — Канал `Them` через Process Tap

**What to build:** Появляется вторая сторона разговора. Пользователь выбирает приложение-источник, и речь собеседника попадает в транскрипт отдельным каналом со своей меткой. С этого момента на экране виден диалог, а не монолог.

**Blocked by:** 03 — Распознавание через WhisperKit.

**Status:** done

- [x] Пользователю показывается список приложений, чей звук можно захватить, включая браузеры
- [x] Звук выбранного приложения попадает в канал `Them` и распознаётся независимо от `You`
- [x] Реплики обоих каналов различимы в транскрипте по метке канала — метка ставится источником жёстко, не выводится из содержимого
- [x] Учтено, что звук браузера отдаёт вспомогательный процесс, а не главный
- [x] Перезапуск приложения-источника обрабатывается: выбор хранится стабильным идентификатором, тап пересобирается сам
- [x] Голос пользователя не появляется в `Them`, речь собеседника не появляется в `You`
- [x] Реализация скрыта за протоколом источника звука; `SessionEngine` не изменён

## Comments

19 тестов. Живая проверка сделана на боевых исходниках, собранных в подписанный бандл, источник — `afplay` с тоном 440 Гц:

```
кадров=374 сэмплов=63824 (3.99 с) RMS=0.2589 пик=0.3662 каналы=them частота=16000
--- источник убит ---   «afplay» сейчас не выдаёт звук. Захват включится сам.
--- источник запущен ---  кадров=353 RMS=0.2484 пик=0.3662
```

Цифры сходятся с сигналом: амплитуда 12000/32768 = 0.366 — ровно измеренный пик, RMS синуса = 0.366/√2 = 0.2589. Тап 48 кГц стерео корректно приведён к 16 кГц моно. За 727 кадров единственное значение метки канала — `them`.

**Живая проверка поймала настоящий баг.** Восстановление после перезапуска источника не срабатывало: захват искал приложение через тот же отфильтрованный список, что и выпадающий список в настройках, а только что перезапущенный процесс регистрируется в Core Audio на мгновение раньше, чем открывает выход, — и фильтр его прятал. Разведено на два пути: список для выбора и разрешение идентификатора для захвата, без фильтра.

**Находка, которую нельзя получить из кодов возврата:** без бандла с `NSAudioCaptureUsageDescription` тап создаётся **успешно** и молча отдаёт нули. Голый CLI-бинарник давал успешный код создания тапа, 372 колбэка IOProc и RMS 0.0. Ошибки нет ни на одном шаге, отладить по возвращаемым значениям невозможно.

Сопоставление процессов с приложением — по трём правилам сразу (PID, bundle-ID с точкой-разделителем, путь внутри бандла), и тапятся **все** процессы приложения. На реальных данных Chrome: главный процесс молчит и живёт в `code_sign_clone`, где в пути вообще нет `.app`; звучит помощник.

**Подключено к сессии** отдельно, вне границ ветки: фабрика сессии переименована из `microphone` в `dualChannel` и собирает оба источника.

**Требует ручной проверки:** живой звонок в браузере — выбрать браузер источником и убедиться, что речь собеседника попадает в транскрипт с меткой `Them`.

**Не сделано, уходит в тикет 10:** статус захвата (`приложение не запущено`, `захват сломался`) отдаётся наружу, но в окне-оверлее не показывается — там ему и место по ADR-0004, а индикаторы состояния это как раз тикет 10.

## Проверено вживую

Канал `Them` захватывает и `afplay`, и Chrome: `пик_rms` 0.08–0.13, реплики закрываются, текст распознаётся.

Дорога сюда стоила отдельного разбора. Тап отдавал буферы правильной формы, целиком заполненные нулями — причиной оказалась ошибка работы с памятью в сведении каналов: взятие адреса `mBuffers` даёт указатель на копию **одного** элемента на стеке, а тап отдаёт два. Подробности и отменённое ошибочное решение — в [ADR-0005](../../docs/adr/0005-vpio-and-process-tap-cannot-coexist.md).

Попутно реализован и измерен второй бэкенд, ScreenCaptureKit: он даёт примерно в 1.5–2.5 раза более громкий сигнал `Them`, потому что пригибание громкости от эхоподавления бьёт по тапу сильнее. Пока переключается только через `defaults`, в интерфейс не выведен.
